Bloco 01 · 09:00–10:30

Do problema
aos requisitos

Antes de pedir código, descubra o que o sistema precisa garantir.

O caso da aula

Uma API para pedidos.

Uma pequena loja precisa registrar pedidos, associar produtos e controlar o estoque.

Produtos

Nome, preço e disponibilidade.

Pedidos

Cliente, itens, total e situação.

Estoque

Quantidade disponível por produto.

O objetivo não é criar um e-commerce completo. É investigar decisões importantes de backend em um domínio pequeno.

O pedido parece simples.

Mas e se alguma etapa falhar? E se o cliente enviar um preço adulterado? E se dois pedidos disputarem a última unidade?

Discussão em duplas

O que ainda não sabemos?

Vocês receberam o seguinte pedido:

“Precisamos de uma API para criar pedidos. O cliente informa os produtos e as quantidades. O sistema calcula o total e atualiza o estoque.”

Em cinco minutos, identifiquem pelo menos cinco perguntas que precisam ser respondidas antes da implementação.

Requisitos

Uma frase não é uma especificação.

Requisito funcional

O sistema permite criar um pedido com um ou mais itens.

Regra de negócio

O total do pedido é calculado pelo servidor a partir dos preços válidos dos produtos.

Restrição

A quantidade de cada item precisa ser um inteiro positivo.

Invariante

Um pedido confirmado não pode deixar o estoque negativo.

Invariantes

O que nunca pode deixar de ser verdade?

  • Todo item pertence a um produto existente.
  • A quantidade de um item é maior que zero.
  • O total é calculado pelo backend.
  • O estoque não pode ficar negativo.
  • Um pedido não pode ser confirmado pela metade.

Um invariante é uma propriedade que o sistema precisa preservar, inclusive quando algo dá errado.

Um requisito ambíguo

“O pedido precisa ser salvo.”

Interpretação A

Salvar o pedido basta, mesmo que a atualização do estoque falhe.

Interpretação B

Pedido e estoque precisam permanecer consistentes quando a operação falhar.

Qual interpretação representa melhor o negócio? Que perguntas precisamos fazer ao responsável pelo produto?

Modelagem

Comece pelas responsabilidades.

←

Diagrama conceitual. As decisões de persistência e as relações finais devem ser justificadas durante a implementação.

Modelagem de dados

O preço de qual momento?

Um produto custa R$ 50 hoje. Amanhã, passa a custar R$ 60.

Preço atual

Representa o valor vigente no cadastro do produto.

Preço praticado no pedido

Registra o valor aplicado naquela compra e preserva o histórico financeiro.

Se o pedido antigo for consultado amanhã, qual preço deve aparecer? Por quê?

Requisito → teste

Se não conseguimos verificar, ainda falta precisão.

Regra

Não permitir quantidade igual a zero.

Verificação

Enviar um pedido com quantidade zero e comprovar que ele não é criado.

Regra

Calcular o total no servidor.

Verificação

Enviar um preço adulterado e confirmar que ele não altera o total.

Bloco 02 · 10:30–12:00

Do requisito
à API

Contrato, responsabilidades e primeira implementação.

Contrato da API

Defina a fronteira antes do código.

POST /api/orders

Cria um pedido com os itens informados pelo cliente.

{
  "customer_id": 42,
  "items": [
    { "product_id": 10, "quantity": 2 },
    { "product_id": 15, "quantity": 1 }
  ]
}

O contrato não aceita preço unitário ou total enviados pelo cliente como fonte de verdade.

Contrato da API

O que a API deve devolver?

{
  "data": {
    "id": 501,
    "status": "confirmed",
    "items": [
      {
        "product_id": 10,
        "quantity": 2,
        "unit_price": "50.00",
        "subtotal": "100.00"
      }
    ],
    "total": "100.00"
  }
}

Exemplo ilustrativo. A estrutura final deve refletir os requisitos acordados e a política de serialização monetária escolhida.

Contrato da API

O contrato também descreve as falhas.

201 Created

Pedido criado com sucesso.

422 Unprocessable Content

Dados de entrada inválidos ou regra de negócio não atendida, conforme o contrato.

404 Not Found

Recurso solicitado não encontrado, quando essa for a semântica definida.

500 Internal Server Error

Falha inesperada. Sem detalhes internos expostos ao cliente.

Os códigos e o formato dos erros devem ser consistentes com a API existente.

Arquitetura mínima

Separar responsabilidades não exige criar vinte classes.

→

→

persistência
  • Controller: traduz HTTP para a chamada de aplicação.
  • Serviço ou caso de uso: coordena a regra de negócio.
  • Modelos e banco: representam e persistem os dados.

A estrutura deve ser proporcional à complexidade. Não criamos abstrações só para preencher pastas.

Exemplo de validação

O cliente fornece os itens, não a verdade financeira.

public function rules(): array
{
    return [
        'customer_id' => ['required', 'integer', 'exists:customers,id'],
        'items' => ['required', 'array', 'min:1'],
        'items.*.product_id' => [
            'required',
            'integer',
            'distinct',
            'exists:products,id',
        ],
        'items.*.quantity' => [
            'required',
            'integer',
            'min:1',
        ],
    ];
}

Exemplo para uma Form Request. A validação de entrada é necessária, mas não substitui as verificações de negócio nem o controle de concorrência.

Bloco 03 · 13:00–14:30

Implementar
não é verificar

O código precisa demonstrar o comportamento esperado.

Estratégia de testes

Teste o comportamento, não a intenção do código.

Teste de feature

Envia uma requisição HTTP e verifica status, resposta e efeitos persistidos.

Teste unitário

Verifica uma regra isolada quando houver lógica que justifique essa fronteira.

Para esta oficina, comecem pelos testes de feature: eles validam o fluxo que o consumidor realmente utiliza.

Teste de feature

Um exemplo em Laravel

public function test_it_creates_an_order(): void
{
    $customer = Customer::factory()->create();
    $product = Product::factory()->create([
        'price' => 50,
        'stock' => 5,
    ]);

    $response = $this->postJson('/api/orders', [
        'customer_id' => $customer->id,
        'items' => [
            [
                'product_id' => $product->id,
                'quantity' => 2,
            ],
        ],
    ]);

    $response->assertCreated();

    $this->assertDatabaseHas('orders', [
        'customer_id' => $customer->id,
    ]);
}

Adaptem os nomes de campos, factories e formato da resposta ao esquema efetivamente implementado.

A pergunta incômoda

Esse teste prova que o total está correto?

O que ele verifica

Que a requisição retorna sucesso e que um pedido foi persistido.

O que ainda falta

Verificar itens, total, preço aplicado, atualização de estoque e comportamento diante de falhas.

Um teste verde só oferece evidência para aquilo que ele realmente verifica.

Exercício 03

Transformem regras em testes.

Implementem testes para:

  • Criar pedido com mais de um item.
  • Rejeitar quantidade zero.
  • Rejeitar produto inexistente.
  • Calcular o total a partir do preço confiável.
  • Não criar pedido quando a validação falhar.

Executem os testes após cada mudança. Não esperem até o final para descobrir se o projeto está funcionando.

IA + testes

Peça testes que possam contrariar a implementação.

Com base nestes requisitos e no código atual:

1. Identifique comportamentos não cobertos.
2. Proponha testes de feature para casos válidos e inválidos.
3. Inclua casos de fronteira e possíveis falhas de consistência.
4. Para cada teste, explique qual regra ele protege.
5. Não altere o código de produção ainda.

Apresente os testes em pequenos incrementos e respeite as convenções existentes no projeto.

Bloco 04 · 14:30–16:00

Engenharia
e revisão crítica

Encontrar o que ainda pode falhar e defender as decisões tomadas.

Revisão em duplas

Troquem de papel.

Dupla implementadora

Apresenta o contrato, as regras implementadas, os testes e as limitações conhecidas.

Dupla revisora

Tenta encontrar uma situação em que o sistema viole uma regra ou aceite um comportamento indevido.

Depois, invertam os papéis. A revisão precisa produzir uma evidência ou uma hipótese reproduzível, não apenas uma opinião.

Desafio de revisão

O cliente envia um total de R$ 1,00.

O valor real dos produtos soma R$ 500,00.

Investiguem

O backend usa o total enviado pelo cliente ou recalcula o valor com base nos dados confiáveis?

Demonstrem

Escrevam uma requisição e um teste que evidenciem o comportamento real.

Desafio de revisão

O estoque falha depois de salvar o pedido.

Simulem ou analisem o ponto de falha entre a persistência do pedido e a atualização do estoque.

  • Quais dados ficam gravados?
  • O pedido pode existir sem a operação estar completa?
  • Uma transação de banco resolve o cenário considerado?
  • Qual teste reproduz a falha e comprova o resultado?

Uma transação local pode garantir atomicidade entre operações no mesmo banco transacional. Não resolve automaticamente falhas em serviços externos.

Desafio de revisão

Dois pedidos disputam a última unidade.

Dois clientes tentam comprar o mesmo produto quase simultaneamente.

Uma consulta de estoque seguida de uma atualização simples pode permitir que duas requisições leiam a mesma quantidade antes de qualquer uma atualizar o registro.

Que estratégia de banco de dados impediria a violação do invariante?

Investiguem atualização atômica, bloqueio apropriado e transação. Não assumam que uma validação feita antes da transação resolve a concorrência.

Uso responsável de IA

O que revisar no código gerado?

Comportamento

O código implementa os requisitos ou acrescenta suposições?

Persistência

As relações, restrições e transações protegem as regras?

Segurança

O sistema confia em valores controlados pelo cliente?

Manutenção

A solução segue as convenções e pode ser compreendida por outra pessoa?

A demonstração final

Mostrem o que conseguem provar.

  • Apresentar o contrato da API.
  • Executar uma requisição válida.
  • Demonstrar um caso inválido.
  • Executar os testes automatizados.
  • Explicar uma decisão de modelagem.
  • Apontar uma limitação que ainda precisa ser resolvida.
