Discussão 01

HTTP 200 não é certificado de qualidade

pedidos.js


app.post('/pedidos', async (req, res) => {
  const pedido = await db.pedidos.criar(req.body);
  estoque.reservar(pedido.itens);   // promise sem await
  res.status(200).json({ status: 'confirmado' });
});
200 OK
{ "status": "confirmado" }
Estoque não reservado

Uma API pode responder rápido, com status 200, e ainda produzir um resultado errado.

Percorra as linhas: o pedido é salvo, a reserva é disparada sem await (se falhar, ninguém fica sabendo) e a resposta diz “confirmado” mesmo assim. Peça outros exemplos de 200 que escondem erro de negócio.

Aprofundamento 03

Parece certo. Até alguém testar o limite.

gerado pela IA


function aplicarDesconto(preco, percentual) {
  return preco - (preco * percentual) / 100;
}

console


aplicarDesconto(50, 10)   // 45   ✓
aplicarDesconto(50, 150)  // -25  ✗ preço negativo

o teste que encontra o defeito


describe('aplicarDesconto', () => {
  test('rejeita percentual acima de 100', () => {
    expect(() => aplicarDesconto(50, 150)).toThrow(RangeError);
  });
  test('rejeita percentual negativo', () => {
    expect(() => aplicarDesconto(50, -5)).toThrow(RangeError);
  });
});

A confiança vem da evidência, não da aparência do código.

Pergunte à turma, antes de revelar o console: o que acontece com 150%? Quem escreveu o teste precisou conhecer a regra de negócio, e isso a IA não sabia.

Aprofundamento 04

Um teste para cada caminho vermelho


describe('POST /pedidos', () => {
  it('422 quando a quantidade é inválida', async () => {
    const res = await api.post('/pedidos').set(auth(maria))
      .send({ produtoId: 7, quantidade: -2 });
    expect(res.status).toBe(422);
  });

  it('403 quando o usuário não pode comprar para o cliente', async () => {
    const res = await api.post('/pedidos').set(auth(joao))
      .send({ clienteId: maria.id, produtoId: 7, quantidade: 1 });
    expect(res.status).toBe(403);
  });

  it('503 e nada salvo quando o banco cai', async () => {
    jest.spyOn(repo, 'salvar').mockRejectedValue(new Error('timeout'));
    const res = await api.post('/pedidos').set(auth(maria))
      .send({ produtoId: 7, quantidade: 1 });
    expect(res.status).toBe(503);
    expect(await repo.contar()).toBe(0);
  });
});
Cada bloco destacado corresponde a um caminho vermelho do fluxograma. O terceiro teste verifica também o efeito colateral: nada pode ficar salvo pela metade.

Aprofundamento 05

Ler, decidir, gravar: a janela da corrida

vulnerável a condição de corrida


async function comprar(produtoId) {
  const { rows } = await db.query(
    'SELECT estoque FROM produtos WHERE id = $1', [produtoId]);
  if (rows[0].estoque < 1) throw new Error('Esgotado');
  // outra requisição pode ler o mesmo valor aqui
  await db.query(
    'UPDATE produtos SET estoque = $1 WHERE id = $2',
    [rows[0].estoque - 1, produtoId]);
}
O intervalo entre o SELECT e o UPDATE é a janela onde a outra requisição entra. Avance (↓) para ver a versão atômica com animação.
Aprofundamento 05

Correção: deixe o banco decidir

operação atômica


async function comprar(produtoId) {
  const { rowCount } = await db.query(
    `UPDATE produtos SET estoque = estoque - 1
      WHERE id = $1 AND estoque >= 1`, [produtoId]);
  if (rowCount === 0) throw new Error('Esgotado');
}

UPDATE condicional

Verificação e escrita numa única instrução.

SELECT … FOR UPDATE

Bloqueia a linha dentro de uma transação.

CHECK (estoque >= 0)

Rede de segurança no próprio esquema.

A verificação e a escrita acontecem no mesmo comando; o banco serializa. As outras duas alternativas são complementares: bloqueio explícito e restrição no esquema.

Autenticado não significa autorizado

Um usuário altera o ID do pedido na URL e consegue acessar o pedido de outra pessoa. Qual é o problema?
GET /api/pedidos/123 GET /api/pedidos/124
Sessão: Maria (token válido)
{ "id": 123, "cliente": "Maria", "total": 89.90 }
{ "id": 124, "cliente": "João", "endereco": "Rua das Flores, 12" }

Autenticação

Quem está fazendo a requisição?

Autorização

Essa pessoa pode acessar este recurso?

IDOR: a API precisa verificar a permissão sobre o recurso, não apenas a validade do token.

Avance uma vez para trocar 123 por 124 na URL. Pergunte por que esconder o botão na interface não resolve. A autorização deve ser verificada no servidor em cada operação. Desça (↓) para o código.

vulnerável


app.get('/api/pedidos/:id', autenticar, async (req, res) => {

Aprofundamento 06

O token diz quem é. A consulta precisa dizer de quem é.

corrigido


app.get('/api/pedidos/:id', autenticar, async (req, res) => {
  const pedido = await Pedido.buscar({
    id: req.params.id,
    clienteId: req.usuario.id,   // o dono do recurso
  });
  if (!pedido) return res.status(404).end();
  res.json(pedido);
});

Por que 404 e não 403? Responder 403 confirma que o pedido 124 existe.

Discuta a escolha 404 vs 403: ambas são defensáveis; 404 evita revelar a existência do recurso.
07Múltipla escolha

Pedido salvo. Estoque não reservado.

O pedido foi salvo, mas a reserva do estoque falhou. O que deveria acontecer?

A operação precisa preservar a consistência do negócio: ou tudo, ou nada.

Aprofundamento 07

Transação local com node-postgres


const client = await pool.connect();
try {
  await client.query('BEGIN');
  const pedido = await criarPedido(client, dados);
  await registrarItens(client, pedido.id, dados.itens);
  await reservarEstoque(client, dados.itens); // lança erro
  await client.query('COMMIT');
} catch (erro) {
  await client.query('ROLLBACK');
  throw erro;
} finally {
  client.release();
}

Mesmo client

Todas as etapas usam a mesma conexão; senão, não estão na mesma transação.

O limite

ROLLBACK não desfaz um e-mail enviado ou um pagamento em outro serviço.

Além do banco

Compensação, saga ou outbox para efeitos externos.

Não prometa que um rollback SQL desfaz qualquer efeito externo. Esse é o gancho para padrões de compensação.

Receber→Validar→Calcular total→Persistir→Confirmar 

app.post('/pedidos', autenticar, async (req, res) => {
  const erros = validarPedido(req.body);
