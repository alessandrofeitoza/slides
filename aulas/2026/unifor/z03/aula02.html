Chave pública

Como combinar um segredo com quem você nunca encontrou?

O problema que ficou de ontem

A ideia: distribuir cadeados abertos

Chave pública = cadeado aberto. Pode dar para todo mundo. Qualquer um tranca.

Chave privada = a única chave que abre. Nunca sai de casa.

Se alguém copiar o cadeado no caminho, não adianta: com ele só dá para trancar.

O par de chaves

Pública

Pode publicar no site, mandar por e-mail, colar no GitHub. Serve para cifrar para você e para conferir sua assinatura.

Privada

Nunca sai do seu computador. Serve para abrir o que cifraram para você e para assinar. Vazou? Troque o par.

É mais lenta que o AES. Por isso, na prática, a chave pública só serve para combinar uma chave simétrica, e o AES faz o trabalho pesado.

Cadeia de confiança: como no cartório

E se a chave privada for roubada?

Revogar

Como bloquear o cartão depois de um roubo: a CA publica que aquele certificado não vale mais (listas CRL e consulta OCSP).

Validade curta

Certificado que vence rápido limita o estrago. Os da Let’s Encrypt são grátis e valem 90 dias, renovados sozinhos (ACME).

Validade curta só funciona com renovação automática. Foi a falta dela que derrubou o Teams.

O que acontece quando o cadeado aparece

Forward secrecy: roubar a chave amanhã não abre o passado

No TLS 1.3 isso é obrigatório. A chave privada do certificado só assina; quem cifra é a chave combinada na hora e jogada fora.

Cadeado não quer dizer site honesto

https://banco-seguro-atualizacao.com

Certificado válido, emitido de graça, em minutos.

O certificado prova que você está falando com aquele nome.

Não prova que o dono do nome é quem você pensa.

Golpes de phishing usam HTTPS o tempo todo. Ensine as pessoas a olhar o nome, não só o cadeado.

Apêndice B: CA interna e certificados

# 1. a CA da clínica
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout ca.key -out ca.crt -days 30 -subj "/CN=CA da Clinica Vida"

# 2. crachá do servidor (API)
echo "subjectAltName=DNS:localhost" > san.ext
openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout api.key -out api.csr -subj "/CN=localhost"
openssl x509 -req -in api.csr -CA ca.crt -CAkey ca.key \
  -CAcreateserial -days 7 -out api.crt -extfile san.ext

# 3. crachá do cliente (laboratório)
openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout lab.key -out lab.csr -subj "/CN=laboratorio-parceiro"
openssl x509 -req -in lab.csr -CA ca.crt -CAkey ca.key \
  -CAcreateserial -days 7 -out lab.crt

Apêndice C: servidor mTLS e testes

# 4. servidor que exige crachá do cliente (deixe rodando)
openssl s_server -accept 8443 -cert api.crt -key api.key \
  -CAfile ca.crt -Verify 1 -verify_return_error -www

# 5. em outro terminal: sem crachá (recusado)
curl --cacert ca.crt https://localhost:8443

# 6. com o crachá do laboratório (aceito)
curl --cacert ca.crt --cert lab.crt --key lab.key https://localhost:8443

Apêndice D: SSH com certificado

# 1. a chave do aluno e a CA SSH
ssh-keygen -t ed25519 -C "aluno@z309" -f ./z309
ssh-keygen -t ed25519 -f ./ca_ssh

# 2. a CA emite o crachá: usuário "aluno", válido por 1 hora
ssh-keygen -s ca_ssh -I aluno-z309 -n aluno -V +1h z309.pub

# 3. ler o crachá: quem, para qual usuário, até quando
ssh-keygen -L -f z309-cert.pub
